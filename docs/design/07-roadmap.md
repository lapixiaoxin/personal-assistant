# 能力演进与里程碑

状态：Proposed v0.2 · 2026-09-24。按成熟度门槛推进，不按固定年份宣称能力。以下数量和阈值是首轮建议，需在真实基线建立后由用户确认。

## 每阶段都保留的架构不变量

用户数据与执行引擎解耦；入口共享领域逻辑；所有真实副作用经过动作门禁；完成需要适当证据；协议变更有兼容方案；未经验证的经验不成为自动流程；自主升级不自行改变权限和验收根。

M0 文档工作与后续里程碑中的运行时能力分开验收。文档齐全不代表 M1 安全边界已经存在。

## 总路线

| 阶段 | 用户得到什么 | 关键建设 | 出口证据 | 本阶段不扩大到 |
| --- | --- | --- | --- | --- |
| M0 定调与可接手工程 | 任一 Agent 能理解现状、按规范接续 | 宪章、架构、基线、SDD、SOP、首个 spec | 文档链路校验；现有 23 测试通过；可追溯工作项 | 新业务运行时 |
| M1 可靠办完一件事 | 有权限边界、有结果证据的任务交付 | 身份、Action Broker、授权摘要、幂等、产物与核验 | 负向绕过测试、真实可逆动作、未知结果对账 | 无人值守长期任务、任意工具执行 |
| M2 持续认识我 | 不反复解释背景，记得目标和承诺 | 持久记忆、来源和纠正、Context、Goal、Conversation | 跨会话偏好复用、撤回生效、导出/恢复、冲突记忆测试 | 自动推断敏感事实、广泛主动执行 |
| M3 会委派、能跟进 | 高价值任务跨天推进，少打扰 | 插件 host、MCP/A2A adapter、持久 scheduler、租约/恢复、通知 | 7天 soak、至少3类故障注入、2种专家/工具协同 | 多节点同时授权写入、无人审批高风险动作 |
| M4 多端存在与范围自治 | 桌面和手机延续同一任务，在规则内代办 | 设备认证、授权同步、离线队列、安静时间、有限委托 | 两端审批/撤销一致、离线重连去重、设备失窃撤销 | 任意物理设备和无限权限 |
| M5 可控自主升级 | 下达能力目标后，Agent 提案、开发、验证并有限发布 | 进化工厂、独立验证、受保护政策、灰度/自动回滚 | 至少3个低风险完整变更；失败版本自动停止；恢复演练 | 自改宪章、提权、放宽测试 |
| M6 长期生活代理 | 工作生活目标协同、更多身体和专业能力 | 决策记忆、跨域目标、设备和本地/云分工 | 各域独立授权、质量与物理安全论证 | 全局无限自治承诺 |

## 阶段依赖

M0 → M1 → M2 → M3 → M4 → M5 → M6 是产品成熟度主线。SDD、离线评测、SOP 和 Agent 开发从 M0 开始并贯穿所有阶段；M5 表示自动发布能力成熟，不表示那时才使用 Agent 开发。

M2 的记忆存储可以与 M1 非重叠开发，但没有 M1 的安全出口证据，不能启用外部写入。M5 的软件工厂基础可在 M3 准备，发布自主权仍等待完整门禁。

## M1 拆分为可交付的小增量

| 工作项 | 依赖 | 交付结果 | 验收方式 |
| --- | --- | --- | --- |
| M1.1 身份与协议 | M0 | 受信 principal、Action/Authorization/Receipt、错误语义；修复请求时间导致的幂等冲突 | 旧 v1 兼容、身份伪造被拒绝、请求重传一致 |
| M1.2 动作代理与范围 | M1.1 | 一种可控本地动作经 broker；权限、参数摘要、预算与撤销 | 越界文件/网络调用被阻止，参数变化重审 |
| M1.3 DSH 接线验证 | M1.2 | 固定版本的工具门禁与隔离策略 | 提示注入及 Shell/curl 绕过负向测试 |
| M1.4 证据与未知结果 | M1.2 | Artifact/Verification、动作回执、结果未知对账 | 外部成功本地断开后不重复执行 |
| M1.5 三场景验收 | M1.3、M1.4 | 会议 brief、研究报告、仓库变更各有真实产物 | 人工验收、耗时记录、SOP 初次成功证据 |

首个可执行规范见 `specs/0001-action-boundary/`；其范围覆盖 M1 最小受控闭环，后续大项继续拆独立 spec。

建议每个开发切片控制在一个 Agent 能完整理解、实现、验证和交接的范围；不要按目录把一个不可验收的大功能机械拆碎。

## 首轮真实样本与门槛

M1 建议先收集 30 个代表任务，覆盖上述三个场景，各至少 10 个；成功按预先明确的验收条件判断。安全负向矩阵必须全部通过，任何越权都阻止扩大范围。至少完成一次真实可逆写入及读回验证，实际对象由专用测试空间承载。

M2 建议建立至少 30 组已标注记忆案例，包括有效偏好、过期事实、冲突、不同 scope 和删除；错误引用关键身份/联系人/授权要求为零，其他记忆 precision 初始目标 ≥95%，同时报告 recall 和样本量。

M3 建议在本机实际休眠、进程退出、网络中断与限流条件下做 7 天 soak；允许失败和等待，但不允许任务悄悄丢失或有副作用动作盲目重复。

M4 的主动提醒初始目标为用户明确评价有价值的比例 ≥80%，至少观察两周；只记录已评价样本会有选择偏差，因此同时报告未评价、忽略和拒绝数量。自动行为限制在已有可信场景。

M5 的三次升级是演练门槛，不是充分的可靠性统计。必须覆盖一次故意不合格候选被拒、一次发布后回归触发自动停止和一次回滚后真实可逆任务成功。

## 产品价值门槛

在 M1 三场景中记录“原本人工完成同质量结果所需时间”和“委托后实际投入”。建议中位 Human Effort Reduction ≥50%，同时报告质量、返工和模型费用；如果只省了生成时间却增加核对与修复成本，应调整场景和流程。

不达标时优先修可靠性、来源和交互，避免通过增加插件数量稀释问题。完成率、成本、耗时需按任务种类、风险和版本分层，不能单一排名。

## 冻结什么，推迟什么

现在确定：所有权、模块端口、动作与授权模型、状态和证据语义、可恢复执行原则、版本兼容、SDD 交付和进化权限边界。

按需求再选：UI 框架、移动端栈、向量/图数据库、云部署、消息队列、MCP/A2A 精确版本、商业化、多用户组织模型、模型微调、物理设备平台。

单用户 ownerId 与数据隔离现在保留，但不预建复杂租户管理。SQLite 持续满足需求就继续使用；出现实际吞吐、远程访问或高可用需求再迁移。

## 里程碑如何作决定

每个出口评审给出结果样本、失败分类、人的时间成本、权限事件、协议变化、恢复证据和下一阶段风险。用户决定是否扩大产品与授权范围；既有范围内的工程切片由 Agent 按规范推进。

若某平台缺少必要阻断/回执能力，收窄该能力范围或更换适配实现，不降低整体契约。若任务没有明确价值，停止该场景试验，但保留可复用的接口与经验。

本路线没有承诺完成日期。得到 M1 的实际吞吐和返工数据后，再估算后续投入，避免以空想的工期驱动架构妥协。
