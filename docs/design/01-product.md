# 产品宪章与体验

状态：Proposed v0.2 · 2026-09-24。原始愿景延续；下述行为与指标是目标要求。

## 产品主体

用户拥有一个持续的助手身份，所有设备、专业 Agent 和工具都服务于这一个身份。助手负责理解目标、记住约束、组织执行、核验结果和对用户负责。专家可以比助手更擅长法律研究、编程或旅行规划；助手必须更了解此刻对用户而言什么重要、什么不能做。

Personal Intelligence Operating System 在这里是产品与架构抽象，不要求替换计算机操作系统。首期是一个本地优先的个人控制与执行系统。

## 不随模型和设备变化的原则

| 原始原则 | 可执行要求 | 反例判定 |
| --- | --- | --- |
| Outcome over Answer | 目标有验收条件；完成有结果证据 | “模型说完成”直接关闭任务 |
| Goal over Feature | 任务关联目标、约束或用户请求 | 为增加工具数量堆接口 |
| Context over Prompt | 主动补齐已授权、相关且新鲜的上下文 | 每次让用户重复介绍自己 |
| Memory over Session | 重要记忆独立于聊天、模型和设备 | 会话结束即丢失承诺 |
| Action over Conversation | 能完成的授权工作推进到结果 | 给操作步骤后停止 |
| Trust over Autonomy | 自动化依赖范围授权与实际证据 | 高成功率自动升级权限 |
| Personalization over Generality | 尊重领域偏好与当前指令 | 把工作中的偏好泛化到家庭 |
| Continuity over Apps | 任务、审批、撤销跨入口一致 | 手机批准后电脑仍执行旧计划 |
| Human Agency over AI Control | 用户可暂停、纠正、导出和离开 | 用通知或依赖感驱动黏性 |
| Compounding over Features | 经验、接口与验证可复用 | 不留版本和证据地修改流程 |

这些原则之间冲突时，裁决顺序为：用户控制权与明确禁止 → 安全及数据边界 → 明确结果与质量 → 连续性与个性化 → 速度、成本和便利。长期偏好不覆盖当前明确指令；外部资料不构成用户指令。

## 目标的三个尺度

**愿望**是尚待澄清的意图，例如“今年想过得健康一点”。助手整理可选方向，不自行定义人生价值或医学目标。

**目标**是可以评估进展的结果，例如“未来八周每周安排两次我能坚持的运动”。保存原因、成功标准、限制和复盘时间。

**任务**是可执行承诺，例如“找出下周两段空闲时间并准备日程草稿”。任务结束不自动代表目标达成。周期性目标记录每个周期结果，不无限复活已经完成的任务。

Goal Graph 先用关系表表达 `parent_of / depends_on / conflicts_with / supports`。只有 `depends_on` 要求无环；人生关系网络不应被强行塑造成一棵树。

## 首批三个代表场景

### 会议准备与承诺跟进

用户：“帮我准备明天下午的项目会议。”

助手读取已授权日历、项目材料和历史决定，识别过期信息，产出可引用的 brief、待决事项和行动项草稿。若资料不足，明确标出缺口；需要向别人索取数据时先准备收件人和内容，按权限决定能否发送。

验收是材料准确、来源可追踪、关键问题已列明、后续承诺可查。首期只产出本地或用户指定文档；写入日历、对外消息和分配他人任务分别是后续动作。

### 持续资料研究与决策记忆

用户：“跟踪这个技术方向，有影响我当前方案的新变化再告诉我。”

助手先记录关注问题、可信来源和何谓重要变化，再按已授权频率检查。相同信息不重复提醒，低置信变化进入待验证列表。结论保留“当时已知、假设、方案、为什么选择、之后如何”的结构。

验收是变化确实相关、证据足够新、通知有价值。不能把研究意见自动变成交易、合同或不可逆决定。

### 仓库改进与能力建设

用户：“给助手接入会议材料准备能力。”

助手先将结果、权限和验收写成规范，在隔离分支实现插件，用脱敏样例和真实测试验证，交付变更、证据、操作 SOP 与回滚方式。当前阶段把发布包交给用户审阅；未来可在既定发布政策内自动发布合格的低风险变更。

验收是功能真的可用、扩展未侵入核心、旧场景不回归，另一名 Agent 能按文档复现。

## 长期体验样例

旅行目标可以持续数周：比较方案、检查证件期限、预算、工作安排、预订准备、行前提醒、途中调整。预订与支付是一系列有独立授权和回执的动作；网络中断时先查订单，不能盲目再买一次。

工作、学习、财务、健康、关系和家庭等领域共用同一套 Goal / Memory / Capability / Action 机制。增加新领域通常需要领域能力与评测包，而不是增加一套总控系统。健康建议、投资研究和关系辅助的验收及权限门槛必须符合该领域，不能沿用文档整理的标准。

## 用户如何掌控助手

用户通常只需要表达目标，看到三个信息：**结果是什么、现在到哪一步、有什么需要我决定**。默认由助手选择模型、专家和工具；高级视图可查看依据、版本、预算和调用链。

核心交互面：

- 目标与承诺：长期方向、当前进展、下次跟进和暂停。
- 任务卡：结果、产物、证据、成本、阻塞原因和下一步。
- 审批卡：具体对象、内容或金额、影响、有效期和撤销方式。
- 个人记忆：知道什么、从哪里知道、适用范围、纠正与删除。
- 活动记录：做过的动作、权限来源、外部回执、失败和修复。
- 全局控制：停止新执行、撤销委托、停用插件、导出数据。

解释呈现可核查的来源、选择摘要和行动理由；不要求保存或展示模型内部思维链。

## 克制的主动性

主动行为有四种输出：静默准备、进入摘要、请求决定、立即提醒。是否打扰取决于时效、价值、证据、可逆性、偏好和已用注意力预算。

“为了证明我在工作”不能成为通知理由。连续忽略同类建议应降低频率；拒绝一次不一定永久禁止，应记录适用范围。紧急提醒仅来自用户预先定义的类别，不由模型临时自封紧急。

## 成熟度不是一个等级

分别记录以下维度，形成每个业务域自己的成熟度档案：

| 维度 | 从低到高的变化 |
| --- | --- |
| 理解 | 单句 → 会话 → 跨任务个人上下文 |
| 记忆 | 候选 → 有来源事实 → 关系与决定 → 可检验程序经验 |
| 执行 | 草稿 → 单动作 → 多步骤 → 长期恢复 |
| 委派 | 固定路由 → 能力发现 → 有预算的专家协作 |
| 主动性 | 响应 → 建议 → 静默准备 → 持续推进 |
| 进化 | 人写代码 → Agent 开发 → Agent 提案和验证 → 受控自主发布 |
| 授权 | 只读 → 准备 → 单次确认 → 范围委托 |

助手可以在会议准备上高度熟练，同时在支付上仍只有观察权限；工程自主发布也不代表有权执行生活中的高风险动作。

## 产品决策规则

新增能力必须回答：它服务什么结果？减少哪类人的负担？产生什么可持续资产？需要什么权限？失败如何收回？如何判断比旧版本更好？

至少有一个高价值场景和可执行验收，否则进入探索清单。商业化、市场和多人组织管理不驱动近期架构；个人数据可迁移、第三方能力可接入的边界现在保留。
