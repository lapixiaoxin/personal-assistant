# SDD 与工程治理

状态：Proposed v0.2 · 2026-09-24。整体为后续开发建议流程；其中“Agent 主动提交到 main”的版本管理规则已按用户本日明确指令生效。本轮不启动业务重构。

## 规范驱动开发的含义

需求、行为、接口、验证与发布要形成一条可追溯链。Agent 开发前知道要达到什么、不能做什么、怎样证明；另一个 Agent 接手时无需重读完整聊天记录。

规范是行为契约，代码是实现，测试是证据，SOP 是验证过的操作知识。任何一项都不能替代其他三项。

## 事实源与文档层级

| 层级 | 位置 | 管理规则 |
| --- | --- | --- |
| 产品原则 | `docs/design/01-product.md` | 改变用户控制权、长期定位须明确决策 |

| 当前能力事实 | `README.md`、`docs/current-state.md` | 只写存在且有证据的能力 |
| 单项变更 | `specs/<id>/spec.md`、`plan.md`、`tasks.md` | 需求、设计、执行分别更新 |
| 验收证据 | `specs/<id>/evidence.md`、`docs/evidence/*` | 绑定环境与产物摘要；失败也记录 |
| 已验证操作 | `docs/runbooks/*` | 区分 verified、candidate、planned |
| 能力维护文档 | 对应模块 README、manifest、contracts | 变更 API/行为时同步 |

冲突时不机械让任一文档“赢”。当前用户指令决定任务授权；宪章/accepted ADR 约束设计；实际行为由代码与验证反映；冲突必须记录并修正规范或实现。Proposed 方案不能被新 Agent 当成已启用功能。

## 标准工作流

1. **Discover**：阅读 Agent 入口、工程基线、相关规范、源码与测试；确认授权、现有改动和依赖。
2. **Specify**：写用户结果、范围、约束、需求 ID、验收、非目标和开放问题。
3. **Design**：写边界、契约、状态、备选取舍、数据迁移、安全、验证与回滚；必要时 ADR。
4. **Review**：重大架构/权限/产品方向由用户决定；明确范围内常规变更按既有授权继续，不重复请求。
5. **Implement**：小切片、契约优先，保持旧版本可运行；复杂或并行工作使用临时分支隔离，验证后集成到 main；记录有实质影响的方案偏差。
6. **Verify**：先相关检查，再必要的完整门禁与真实操作；受保护验收不能为通过而放宽。
7. **Document**：更新事实、接口、证据、SOP、迁移和交接；成功经验与未验证方案分开。
8. **Release / Observe**：在已有发布授权内灰度，检查实际结果；没有发布授权时交付完整可审阅包。

审查不等于每一步停下来问人。需要人的决定集中于目标、权限和不可逆承诺；证据收集、文档、可逆实现和检查由 Agent 完成。

## 最小变更包

`spec.md`：目标、范围、术语、FR/NFR、acceptance、风险、开放问题。

`plan.md`：实现边界、接口、数据、备选、迁移、验证、回滚。

`tasks.md`：任务 ID、依赖、状态、负责角色、产物、验收引用。

`evidence.md`：revision/tree digest、执行环境、真实命令、退出码、结果、未跑项、日志位置和脱敏说明。

小型文档/低风险修复可以合并成一份简短变更记录，不为改错字创建全套空模板。涉及新能力、权限、协议、持久化或运行时行为时使用完整变更包。

## 需求到证据的追溯

示例链：`FR-003 审批参数绑定 → AC-003 参数改变拒绝执行 → T-04 authorization 检查 → contract/integration case → evidence E-04 → release artifact digest`。

需求 ID 稳定；删除或改义必须记录原因。验证结论不能只有“测试通过”；应能定位运行了哪些用例、使用什么 fixture、实际环境是否含真实外部服务。

## Definition of Ready

目标和非目标清楚；范围授权可判定；关键契约与迁移已设计；主要失败模式有验收；测试资源可获得或有明确封锁项；不存在影响正确性的关键未知。未知若不影响当前独立切片，可以推进该切片并保留开放项。

## Definition of Done

行为符合需求；相关检查通过；关键契约兼容；真实测试按风险完成；安全负向通过；产物与证据可追踪；文档、SOP、版本和迁移同步；回滚可用；遗留项没有被标成完成。

“Implemented”可以成立而“Verified”尚未成立，必须分别标注。任务完成不能因为 token 或时间预算耗尽而改写验收。

## 对 Agent 友好的仓库

根 AGENTS.md 保持短而明确，提供入口和不变量，不复制全套设计。模块 README 解释职责、公开端口、运行方式、依赖和典型失败。lumi 的模块生产代码放在 `<module>/src/`，模块测试放同级 `<module>/tests/`；跨模块测试放在根 `tests/`，目前有 `contract/`，后续按需求增加 integration / scenario / live / recovery。已有测试按 [SPEC-0002](../../specs/0002-lumi-workspace/spec.md) 迁移，具体运行方式见 [测试约定](../../tests/README.md)。

能力新增采用 `adapters/<system>`、独立模块或插件，不往 Core 中累计业务条件分支。没有真实调用方时不预建抽象。每个可扩展端口至少有一个实际 provider 和 consumer。

版本管理由 Agent 托管：完成已授权工作及必要验证后，主动提交到本地 `main`，无需逐次请求提交许可。常规变更直接形成小而完整的提交；复杂或并行工作可使用 `feat/<spec-id>-<slug>` 或 `fix/<spec-id>-<slug>` 临时分支/worktree，验证后由 Agent 集成回 main。提交前检查差异、暂存范围和必要证据，保护用户无关改动，不提交私人数据或凭据。交付报告包含 commit 与验证结果；远端 push 和部署按具体授权执行。操作标准见仓库 `docs/runbooks/version-control.md`。

## CI 分阶段

当前：lint → typecheck → DSH 版本对齐 → Vitest → build。

M1 增加：文档链接和状态检查、契约样例校验、依赖边界、迁移、授权负向、动作未知结果。

M2–M4 增加：记忆纠正/删除、场景评测、持久恢复、跨入口、设备撤销。真实外部测试按授权环境 opt-in，不让 fork PR 拿生产秘密。

M5 增加：独立保留评测、供应链摘要、构建证明、受保护发布政策、灰度和自动回滚。CI 本身的修改按风险审查。

本次只建立流程和模板；未安装 spec-kit、未新建全部 CI，也不把 Markdown 描述视为自动门禁。

## ADR 与规范变更

涉及跨模块依赖、外部协议、数据所有权、执行引擎、授权或数据迁移时建立 ADR：背景、备选、决定、后果、验证、撤销条件。没有真实选择的常规实现不制造 ADR。

需求变化先更新 spec 和影响分析，再继续实现；紧急修复可先止损，但恢复后必须补齐证据和规范。已发布行为的兼容变更需要版本与弃用计划。

## 接手与知识复利

handoff 保存已完成事实、当前工作、具体失败、下一步命令、授权范围、相关 spec 和证据。不要保存秘密、整段聊天和不稳定推测。

每次真实成功后判断：是否可复用？是否补齐现有 SOP？是否与已有经验冲突？是否需要复现？经验只有在证据与边界明确后才升为 verified。定期检查 SOP 是否因依赖升级失效。
