# 自主进化与软件工厂

状态：Proposed v0.2 · 2026-09-24。SDD 工作方式现在建立；运行时自主升级尚未实现。

## 进化的对象

助手可进化的部分包括个人理解、程序经验、能力发现与选择、规划策略、记忆检索、执行适配、评测和工程实现。进步必须表现为同类结果更可靠、更省心或成本更低，而非修改更多代码。

无需先训练专属模型。优先通过可修正记忆、版本化 SOP/Skills、策略配置和插件实现积累能力；模型微调只有在拥有授权数据、明确收益及独立评测后才进入单独方案。

## 五种改进路径

| 类型 | 例子 | 验证与发布边界 |
| --- | --- | --- |
| 个人知识更新 | 用户更改偏好 | 用户指令、来源与 scope；敏感推断仍候选 |
| 程序经验沉淀 | 成功整理会议 brief 的步骤 | 验收证据、前置条件、另一轮复现 |
| 能力配置优化 | 在研究任务改用更合适模型 | 固定评测、成本与出境范围不扩大 |
| 插件升级 | 增加日历连接器 | SDD、隔离开发、契约与真实验收、回滚 |
| 核心/安全机制升级 | 修改授权或状态机 | 受保护变更，独立审查与明确批准 |

不同类型不共用一个“自动进化”开关。学习习惯不授权修改代码；修改代码不授权部署；部署不授权访问更多个人数据。

## 从成功操作到可复用能力

闭环：任务证据 → ExperienceCandidate → 去隐私与归因 → SOP 草案 → 沙箱复现 → 适用边界 → 受控发布 → 真实使用监测 → 保留/修订/退役。

经验候选必须包含：问题类型、前置条件、使用版本、已授权动作、关键步骤、预期观察、失败判别、停止与回滚、验证者、证据引用、成本和已知局限。

一次成功只证明“此环境下成功过”。建议至少两次独立复现、覆盖一个失败/边界条件，且有真实结果验收后，才能标成通用 verified SOP。计数是初始治理建议，不是统计可靠性证明；高风险流程需要更多独立证据。

SOP 使用参数化对象和脱敏样例；不能把收件人、真实凭据、数据库路径或私人材料硬编码成下一次的默认值。

失败经验也要保存，但位于 incident/diagnostic 记录，写“尝试失败、证据和不再尝试的条件”，不得混进成功操作步骤。过期或上游不兼容的 SOP 立即降级，停止自动复用。

## 变更提案的来源

用户命令、重复失败、用户反复纠正、能力缺口、插件/上游更新、评测回归和成本异常都可以生成提案。它们只能进入 backlog，不直接启动无限开发。

提案排序考虑用户价值、出现频率、风险、工作量、能否验证和当前目标优先级。系统给维护与探索设置总预算，探索不应挤占已承诺的用户任务。

## 软件工厂的状态机

`proposed → specified → approved_to_build → building → validating → ready_to_release → canary → active → retired`

任一步失败返回带原因的前一阶段；发布异常进入 `rollback_required / rolled_back`。暂停、拒绝和被替代是显式状态，不靠删除提案掩盖。

每次变更绑定 spec ID、需求版本、base commit/tree digest、候选源码摘要、构建产物摘要、依赖锁、验证配置、数据迁移和回滚包。

### 分工与独立性

Planner 形成目标与规范；Builder 在隔离分支实现；Verifier 验证需求与安全；Release Controller 校验发布政策并切换版本；Observer 观察新版本结果。初期可以由同一个模型分不同任务承担，但关键权限、测试输入和发布凭据必须隔离。

让“另一个 Agent 看一下”不是独立性保证。Verifier 应运行受保护的测试入口和版本固定的评测集，不使用 Builder 自报分数；Release Controller 校验精确产物摘要，不接受“测试过类似代码”的证明。

### 开发环境

开发 Agent 领取任务所需代码和脱敏 fixture，使用 feature branch/worktree 或独立 checkout。不能直接编辑运行中的工作区、生产数据和发布政策。若仓库尚无初始 commit，先保存可追踪初始基线，不能虚构可回滚 commit。

工作项可以并行，但要有文件/模块责任边界、共享契约协调人、集成顺序与冲突处理。所有任务的进度写在 spec/tasks 和交接记录，防止新 Agent 依赖隐形聊天上下文。

## 发布门禁

发布控制器至少检查：

1. 需求及验收已固定，风险分类由受保护规则决定；
2. 当前 base 与候选产物匹配，依赖与构建可复现；
3. 契约、场景、权限负向、真实操作和恢复测试满足该风险级别；
4. 新版本相对基线无不可接受回归，预算和数据出境不扩张；
5. 文档、SOP、能力清单、迁移及回滚已更新；
6. 发布授权有效，签名与部署目标匹配。

Builder 不能通过改低阈值、删除困难样例、伪造测试报告或扩大 `allowed_paths` 获得通过。测试新增是正常开发；删除/放宽受保护基线必须单独审查，旧评测版本仍保留可比较。

## 自动化等级

| 等级 | 可自主完成 | 人的决策点 |
| --- | --- | --- |
| E0 | 汇总证据、提出改进 | 选择需求与方案 |
| E1 | 按批准 spec 写代码、测试和文档 | 评审变更与发布 |
| E2 | 自动提案、复现、构建、独立验证 | 批准新范围与上线 |
| E3 | 在既定政策内发布低风险插件/配置 | 改变政策、扩大权限和高风险变更 |
| E4 | 维护长期能力组合并自动回滚 | 宪章、安全根、重要架构及高影响决策 |

M0–M4 使用 E0–E2；M5 才试点 E3。E4 是远期方向，不承诺通用无人维护。

## 灰度与回滚

先离线基准，再影子执行，再有限真实任务灰度，最后提升覆盖率。影子执行默认禁止副作用；不能把同一个邮件/订单交给两版同时执行来比较。

建议低风险插件以明确任务类型和小样本灰度，不把所有用户任务随机送入未知版本。错误、成本、延迟、人工接管或权限异常超过预设阈值时停止派单并回滚。

模型、插件、配置、检索策略、SOP 和数据版本都要记录。代码回滚通常切回上一产物；数据迁移需兼容设计；已经发生的外部动作只可补偿或对账。回滚后用真实可逆任务确认恢复。

## 评测防投机

固定公开回归集 + 独立保留集 + 真实灰度构成证据。小样本成绩标明数量与不确定性，不能用 5/5 宣称 100% 可靠。

用户反馈、人工接管和错误账单是外部事实源。模型自评可辅助解释，不能单独证明结果正确。优化目标包含质量与安全约束，防止系统通过拒绝困难任务、过度打扰或转嫁人工成本提高表面成功率。

## 一次具体的自主升级

用户：“以后能自动准备我的项目会议材料。”

助手记录预期结果和权限 → 发现缺少 calendar reader → 建立 SPEC → 用沙箱日历和脱敏项目材料实现 connector/workflow → 独立检查来源引用、缺失资料与权限 → 真实测试日历读取和草稿生成 → 形成 verified SOP → 发布已批准的只读版本 → 观察数次实际会议使用 → 再提案申请持久触发与静默准备。

这个过程逐步增加能力，保留同一目标、任务、授权和证据模型；不会因为“会议能力变复杂”重写整体架构。
