# ADR-001：独立个人控制层，模块化单体起步

状态：Proposed · 2026-09-24。关联：设计 02/03、M0–M3。

2026-10-13：独立通用协调与 SDK adapter 的未来实施建议部分 Superseded by [ADR-007](0007-dsh-server-and-channel-boundary.md)。个人资产独立、模块化与控制原则仍有效；本文保留历史取舍。

2026-09-25：[ADR-003](0003-dsh-centered-harness.md) 细化选项 4：DSH 为唯一认知与工具编排 Harness，lumi Host 提供确定性服务，Cordis 插件桥接其端口。个人资产独立与模块化单体原则保持不变。

## 背景

现有 TS Core、SQLite Ledger、DSH adapter 已分离，测试基线可运行。长期需要换模型、工具、专业 Agent、记忆实现和入口，个人资产需连续存在。单用户当前不需要分布式控制面。

## 备选

1. 全部放入 DSH 插件：短期少一层，但个人身份与记忆受上游会话模型约束。
2. 自研 Harness：控制最大，但重复模型循环、工具和 SDK 的基础建设。
3. 全面微服务：独立部署，但提前引入分布式事务、认证与运维负担。
4. 独立控制层 + DSH adapter + 模块端口：维护契约映射，换来个人资产连续和渐进拆分。

## 建议决定

采用 4。继续 TS/pnpm/SQLite；学习 DSH/Cordis 的依赖声明、类型化服务、生命周期释放，不把 Cordis 引入 Core 作为必要前提。

业务能力、记忆 provider、策略、验证器和模型都可以替换。端口随真实 provider/consumer 形成，不预建全套空包。先按数据所有权分模块，再按隔离与部署需求拆进程。

## 后果、验证与撤销

需维护领域版本、adapter 映射和跨入口契约。新增能力不改 Core 的业务分支；替换 executor 不迁移个人数据；旧 API 通过兼容测试。

当固定 DSH 版本无法提供必需的执行门禁且无法通过安全接线补齐时，先限制能力，再用新 ADR 决定升级、fork 或更换引擎。当真实容量或高可用需求超过单节点时，再设计数据库与控制节点迁移。
